Full gate run: version audit, build/test/lint/doc gates, cross-architecture check, packaging, FFI sanitizers, and a five-lens soundness audit of cross-object pairing.

Verdict

NO-GO

Every build, test, lint and documentation gate passes, and the crate packages cleanly. The release is blocked by the soundness audit alone: six confirmed memory-safety defects reachable from 100% safe Rust, each with a repro that was executed and observed to fault. Five of the six are the same bug class as the one this branch set out to fix: a guard that compares only mjModel::signature(), which pins the element counts but no buffer size below them.

The accepted residual is no longer residual. The earlier decision to drop flex_elemlayer from MjvScene::is_compatible rested on my statement that no model pair could exercise it. That statement was wrong. A brute-force search over 5-tetrahedron meshes on 8 vertices found a pair, and the overflow reproduces from a program compiled with #![forbid(unsafe_code)].

Blocking items

  1. B1 -- MjvScene::is_compatible omits flex_elemlayer: heap write past the flex face buffer (SIGABRT).
  2. B2 -- MjData::try_swap_model: signature-only guard, out-of-bounds read then SIGSEGV in reset().
  3. B3 -- MjData::copy_state_from_data: signature-only guard, out-of-bounds read (SIGSEGV).
  4. B4 -- MjXInfo::view / view_mut in src/util.rs: cached ranges from another model (SIGSEGV).
  5. B5 -- MjData::copy_to / copy_visual_to: signature-only guard; mj_setPtrData relays the source layout onto the destination.
  6. B6 -- MjvFigure::draw: publicly writable linepnt reaches mjr_figure unclamped.
  7. B7 -- rustdoc gate fails: MjvScene's public doc links to the pub(crate) method is_compatible.

Soundness audit -- cross-object pairing

Five parallel lenses swept the codebase for the shape the MjvScene fix addressed: a wrapper caches sizes derived from object A, then a safe method accepts object B and lets C index A's allocation with B's quantities. Every suspected finding then went to an independent refuter that had to run the repro.

Reconciliation

38 findings raised across 5 lenses. 21 were OK notes (examined and cleared). 17 needed adversarial confirmation. Round 1 confirmed 5 and rejected 3, then hit a cap of 8, leaving 9 unverified. Round 2 re-ran all 9; all 9 survived. Total: 14 confirmed, 3 rejected, 0 unverified. 17 = 14 + 3, and 38 = 17 + 21. No spawned agent was dropped in either round.

Standing hazard worth one line of .gitignore

.gitignore:4 ignores target only. Any untracked directory that is not ignored is packaged into the .crate. This gate run proved it: its own target-asan/ scratch dir put .rustc_info.json inside the archive. The same applies to output_renderer/ and output_renderer_asset_reupload/, which examples/visualization/renderer/renderer.rs and its siblings write into the repo root and which nothing ignores. Running that example and then packaging would ship the PNGs; the run measured 198 MB. All of this gate run's scratch directories have been deleted and the tree is clean, so nothing blocks the release today.

Generated artifacts belong in .gitignore, never in Cargo.toml exclude. Adding /target-* and /output_renderer* closes it.

Manual maintainer steps

Not runnable by the agent: every step below is networked or rewrites history. Do not start these until the blockers above are resolved.

  1. Merge develop into main by PR, titled "Merge changes for release of 6.0.0 (MuJoCo 3.12.0)".
  2. Tag the merge commit on main:
    git tag 6.0.0 && git push origin 6.0.0
  3. Create and push the release branch:
    git switch -c v6.0.x && git push -u origin v6.0.x
  4. Publish the GitHub release for tag 6.0.0. This triggers .github/workflows/tests.yml on Ubuntu and Windows; wait for green.
  5. Publish to crates.io, with the same link path set so the verify build links:
    export MUJOCO_DYNAMIC_LINK_DIR=$(realpath mujoco-3.12.0/lib)
export LD_LIBRARY_PATH=$MUJOCO_DYNAMIC_LINK_DIR
cargo publish
  6. Confirm the docs.rs build succeeded, that readthedocs shows a v6.0.x version, and that docs.rs/mujoco-rs/6.0.0 and the badge links resolve.

Method

Phases 0 to 2 ran inline: release context, version-string audit, and the release-specific changelog checks. Phases 3 and 4 ran as a two-track workflow, 22 agents. Track 1 ran the cargo gates serially on the shared ./target so the dependency cache stayed warm. Track 2 ran the Sphinx build, the RST example check, the changelog completeness diff against tag 5.0.0, the five soundness lenses, and the sanitizers, each with its own CARGO_TARGET_DIR and its own MuJoCo build directory. A second workflow of 10 agents confirmed the findings that the first round's cap left unverified. Both rounds reconciled spawned against returned agents; neither dropped one.

ASan and UBSan ran the full 308-test library suite against a from-source MuJoCo build with -fsanitize=address,undefined. Miri ran the basic example against a Miri-instrumented shared library.
